# Requirements Document

## Introduction

GitPulse is an AI-powered Git Recovery Assistant built for the AWS SBG JISU GenAI Sprint 1.0, Track 3: Build with Kiro. GitPulse is a web application that helps college students, beginner programmers, and developers diagnose common Git errors and recover safely, instead of blindly running destructive commands copied from StackOverflow.

The user pastes a Git error message, terminal output (such as `git status` or `git reflog`), or a plain-language description of a Git problem, or selects one of 5 built-in sample incidents. GitPulse identifies the likely incident type, separates detected evidence from assumptions, explains the problem in beginner-friendly language, and presents an ordered, safety-first recovery plan. GitPulse flags destructive and risky commands, explains their command-specific consequences, and requires command-specific inspection or preservation steps before each risky action. Safeguard steps reduce risk but do not remove it, so GitPulse keeps risky steps labeled as risky after safeguards are added.

GitPulse runs a dual-mode analysis engine:
1. Amazon Bedrock AI Mode (`bedrock_ai`): an optional serverless endpoint (AWS Lambda) that calls Amazon Bedrock when AWS credentials and endpoint configuration are provided.
2. Deterministic Safe Fallback / Demo Mode (`fallback_demo`): a rule-based pattern-matching diagnosis engine in the client layer, used when the Bedrock endpoint is unavailable.

The frontend is built with React, TypeScript, Vite, Tailwind CSS, Lucide React icons, and Vitest. The frontend deploys as a static build on AWS Amplify Hosting (or Vercel/Netlify) with no mandatory backend dependency. The full core workflow works in `fallback_demo` mode. GitPulse has no database, no user authentication, no GitHub OAuth, and no live repository integration. No part of GitPulse (Dashboard, Analyzer, Fallback_Engine, Safety_Validator, or Bedrock_Handler) executes Git commands, reads or modifies the user's repository, or contacts Git remotes. The user inspects every suggested command and decides whether to run the command manually in a terminal.

Safeguard steps such as `git status` and `git stash push -u` reduce risk but do not guarantee safety. Adding or detecting safeguard steps never lowers the risk level of a risky command and never removes its warnings.

Implementation priority: the deterministic fallback core app (Dashboard, Fallback_Engine, Sample_Incidents, Safety_Validator, History_Store) and the Test_Suite are the first implementation priority. The Amazon Bedrock / AWS Lambda integration is optional and must not block building, testing, or deploying the working core app.

## Glossary

- **GitPulse**: The complete web application described in this document, including the Dashboard, Analyzer, Safety_Validator, History_Store, and the optional Bedrock_Handler.
- **Dashboard**: The single-page React user interface of GitPulse.
- **Incident_Input**: The text area on the Dashboard where the user enters a Git error message, terminal output, or problem description.
- **Incident_Text**: The string content submitted from the Incident_Input for analysis.
- **Sample_Incident**: One of 5 built-in example Incident_Text values, one for each Supported_Incident_Type.
- **Supported_Incident_Type**: One of the values `rejected_push`, `merge_conflict`, `detached_head`, `stuck_rebase`, `lost_commits`.
- **Incident_Type**: A Supported_Incident_Type or the value `unknown`.
- **Analyzer**: The analysis orchestration module that selects an Analysis_Mode, produces an Analysis_Result, and passes the Analysis_Result through the Safety_Validator.
- **Fallback_Engine**: The deterministic, rule-based pattern-matching diagnosis engine that runs in the client layer and produces Analysis_Results with `analysisMode` set to `fallback_demo`.
- **Bedrock_Handler**: The optional AWS Lambda handler located at `backend/lambda/analyzeIncident.ts` that calls Amazon Bedrock and returns Analysis_Results with `analysisMode` set to `bedrock_ai`.
- **Bedrock_Endpoint_URL**: The build-time frontend configuration value that holds the HTTPS URL of the deployed Bedrock_Handler.
- **Analysis_Mode**: Either `bedrock_ai` (result generated by Amazon Bedrock through the Bedrock_Handler) or `fallback_demo` (result generated by the Fallback_Engine).
- **Analysis_Result**: The shared TypeScript data object exchanged between the Analyzer and the Dashboard, containing the fields `incidentType`, `title`, `confidence`, `severity`, `analysisMode`, `summary`, `detectedEvidence`, `assumptions`, and `recoverySteps`.
- **Recovery_Step**: One element of `recoverySteps`, containing `stepNumber`, `title`, `explanation`, `command`, `riskLevel`, an optional `warningMessage`, and an optional `backupPrerequisite`.
- **Risk_Level**: One of `safe`, `caution`, `destructive`, assigned to each Recovery_Step. The severity order is `safe` < `caution` < `destructive`.
- **Destructive_Command**: A Git command that can permanently discard work or overwrite shared history, matching any of these forms: `git reset` with the `--hard` option; `git push` with the `--force` option or the `-f` option (excluding `--force-with-lease` when used without `--force` or `-f`); `git clean` with the `-f` or `--force` option, alone or combined in a short-option group such as `-fd`, `-fx`, or `-fdx`; `git checkout` with the `-f` or `--force` option; `git branch` with the `-D` option or with both a delete option (`-d` or `--delete`) and a force option (`-f` or `--force`).
- **Caution_Command**: A Git command that is risky but less destructive than a Destructive_Command and is never classified `safe`. The only Caution_Command is `git push` with the `--force-with-lease` option (including `--force-with-lease=<ref>`) and without the `--force` or `-f` option.
- **Risky_Command**: A Destructive_Command or a Caution_Command.
- **Risky_Step**: A Recovery_Step whose `command` contains at least 1 Risky_Command.
- **Safeguard_Step**: A Recovery_Step with Risk_Level `safe` whose command is an inspection or preservation command required before a specific Risky_Command, such as `git status`, `git stash push -u`, `git clean -nd`, `git fetch origin`, `git log --oneline HEAD..origin/<branch>`, or `git branch --no-merged`. A Safeguard_Step reduces the risk of the Risky_Command that follows it and does not guarantee that the Risky_Command is safe; the presence of Safeguard_Steps never changes the Risk_Level of the Risky_Step to `safe`.
- **Safety_Overclaim_Phrase**: Any of the case-insensitive phrases "now safe", "makes it safe", "safe to run", "completely safe", "guarantees safety", or "fully protected", when applied to a Risky_Step or to the effect of a Safeguard_Step.
- **Safeguard_Set**: The ordered list of Safeguard_Steps that a specific Risky_Command requires, as defined in Requirements 12 through 15.
- **Safeguard_Window**: For a Risky_Step, the Recovery_Steps located after the nearest preceding Risky_Step (or after the start of `recoverySteps` when no preceding Risky_Step exists) and before the Risky_Step.
- **Residual_Risk_Label**: The exact text "Risk remains after safeguards", which marks a Risky_Step as still risky after its Safeguard_Steps are added.
- **Safety_Validator**: The module that inspects every Analysis_Result before display, classifies Risky_Commands, adds command-specific warnings, and inserts missing Safeguard_Steps.
- **Test_Suite**: The set of Vitest unit tests included in the GitPulse repository.
- **Detected_Evidence**: Entries in `detectedEvidence` that quote or describe text actually found in the Incident_Text.
- **Assumptions**: Entries in `assumptions` that describe inferences not directly proven by the Incident_Text.
- **Mode_Badge**: The visual label on the Dashboard that shows the Analysis_Mode of the displayed Analysis_Result.
- **Risk_Badge**: The color-coded label on each Recovery_Step showing its Risk_Level.
- **History_Store**: The module that persists recent Analysis_Results in the browser `localStorage`.
- **History_Entry**: One stored record in the History_Store, containing the Incident_Text, the Analysis_Result, and a creation timestamp.
- **History_Panel**: The Dashboard section that lists History_Entries.

## Requirements

### Requirement 1: Incident Input

**User Story:** As a beginner developer, I want to paste a Git error, terminal output, or a description of my problem, so that GitPulse can diagnose what went wrong.

#### Acceptance Criteria

1. THE Dashboard SHALL display the Incident_Input as a multi-line text area that accepts Git error messages, terminal output, and plain-language problem descriptions.
2. THE Dashboard SHALL display an "Analyze Incident" button next to the Incident_Input.
3. WHEN the user activates the "Analyze Incident" button with an Incident_Text containing at least 1 non-whitespace character and at most 20,000 characters, THE Analyzer SHALL start analysis of the Incident_Text.
4. IF the user activates the "Analyze Incident" button while the Incident_Input contains only whitespace or is empty, THEN THE Dashboard SHALL display an inline validation message stating that incident text is required and SHALL keep the Analyzer idle.
5. IF the Incident_Text exceeds 20,000 characters, THEN THE Dashboard SHALL display an inline validation message stating the 20,000-character limit and SHALL keep the Analyzer idle.
6. THE Dashboard SHALL display the current character count of the Incident_Input next to the 20,000-character limit.
7. WHEN the user activates the reset control, THE Dashboard SHALL clear the Incident_Input, clear any validation message, and clear the displayed Analysis_Result.

### Requirement 2: Sample Incidents

**User Story:** As a student exploring GitPulse, I want one-click sample incidents, so that I can see how GitPulse handles each common Git problem without reproducing the error myself.

#### Acceptance Criteria

1. THE Dashboard SHALL display 5 Sample_Incident buttons, one for each Supported_Incident_Type: rejected push, merge conflict, detached HEAD, stuck rebase, and lost commits.
2. WHEN the user activates a Sample_Incident button, THE Dashboard SHALL replace the content of the Incident_Input with the Incident_Text of the selected Sample_Incident.
3. WHEN the user activates a Sample_Incident button, THE Dashboard SHALL visually mark the selected Sample_Incident button as active.
4. WHEN the user edits the Incident_Input after selecting a Sample_Incident, THE Dashboard SHALL remove the active marking from the Sample_Incident button.
5. FOR ALL Sample_Incidents, WHEN the Fallback_Engine analyzes the Sample_Incident Incident_Text, THE Fallback_Engine SHALL return an Analysis_Result whose `incidentType` equals the Supported_Incident_Type of that Sample_Incident.

### Requirement 3: Rejected Push Diagnosis

**User Story:** As a developer whose push was rejected, I want GitPulse to explain why and how to integrate remote changes safely, so that I avoid overwriting teammates' work with a force push.

#### Acceptance Criteria

1. WHEN the Incident_Text contains `[rejected]` together with `non-fast-forward`, `fetch first`, or `Updates were rejected`, THE Fallback_Engine SHALL return an Analysis_Result with `incidentType` set to `rejected_push`.
2. WHEN the Fallback_Engine returns a `rejected_push` Analysis_Result, THE Fallback_Engine SHALL include Recovery_Steps that inspect the local state with `git status`, fetch remote changes with `git fetch`, and integrate remote changes with `git pull --rebase` or `git merge` before pushing again.
3. WHEN the Fallback_Engine returns a `rejected_push` Analysis_Result, THE Fallback_Engine SHALL include, in the `summary`, a beginner-friendly explanation that the remote branch contains commits missing from the local branch.

### Requirement 4: Merge Conflict Diagnosis

**User Story:** As a beginner facing a merge conflict, I want step-by-step guidance to resolve or abort the merge, so that I can finish the merge without losing changes.

#### Acceptance Criteria

1. WHEN the Incident_Text contains `CONFLICT (` or `Automatic merge failed` or `fix conflicts and then commit`, THE Fallback_Engine SHALL return an Analysis_Result with `incidentType` set to `merge_conflict`.
2. WHEN the Incident_Text contains `Merge conflict in <path>`, THE Fallback_Engine SHALL include each conflicted file path in `detectedEvidence`.
3. WHEN the Fallback_Engine returns a `merge_conflict` Analysis_Result, THE Fallback_Engine SHALL include Recovery_Steps that list conflicted files with `git status`, explain the `<<<<<<<`, `=======`, and `>>>>>>>` conflict markers, stage resolved files with `git add`, and complete the merge with `git commit`.
4. WHEN the Fallback_Engine returns a `merge_conflict` Analysis_Result, THE Fallback_Engine SHALL include a Recovery_Step that describes `git merge --abort` as the option to return to the pre-merge state.

### Requirement 5: Detached HEAD Diagnosis

**User Story:** As a developer in a detached HEAD state, I want to understand what detached HEAD means and how to keep my work, so that commits made in that state are not lost.

#### Acceptance Criteria

1. WHEN the Incident_Text contains `detached HEAD` or `HEAD detached at` or `HEAD detached from`, THE Fallback_Engine SHALL return an Analysis_Result with `incidentType` set to `detached_head`.
2. WHEN the Fallback_Engine returns a `detached_head` Analysis_Result, THE Fallback_Engine SHALL include a Recovery_Step that preserves the current commit on a new branch with `git switch -c <branch-name>` or `git branch <branch-name>` before any Recovery_Step that changes branches.
3. WHEN the Fallback_Engine returns a `detached_head` Analysis_Result, THE Fallback_Engine SHALL include, in the `summary`, a beginner-friendly explanation that HEAD points to a commit instead of a branch.

### Requirement 6: Stuck Rebase Diagnosis

**User Story:** As a developer stuck in an unfinished interactive rebase, I want clear options to continue, skip, or abort, so that I can exit the rebase without corrupting history.

#### Acceptance Criteria

1. WHEN the Incident_Text contains `rebase in progress` or `interactive rebase in progress` or `git rebase --continue` or `could not apply`, THE Fallback_Engine SHALL return an Analysis_Result with `incidentType` set to `stuck_rebase`.
2. WHEN the Fallback_Engine returns a `stuck_rebase` Analysis_Result, THE Fallback_Engine SHALL include Recovery_Steps that inspect the rebase state with `git status`, describe `git rebase --continue` after resolving conflicts, and describe `git rebase --abort` as the option to return to the pre-rebase state.
3. WHEN the Incident_Text contains `onto <commit-hash>`, THE Fallback_Engine SHALL include the commit hash in `detectedEvidence`.

### Requirement 7: Lost Commits Diagnosis

**User Story:** As a developer who ran an accidental reset, I want GitPulse to show me how to find and restore lost commits through the reflog, so that I can recover my work.

#### Acceptance Criteria

1. WHEN the Incident_Text contains `reset: moving to` or `HEAD@{` or `git reset --hard` or a description mentioning lost commits, THE Fallback_Engine SHALL return an Analysis_Result with `incidentType` set to `lost_commits`.
2. WHEN the Fallback_Engine returns a `lost_commits` Analysis_Result, THE Fallback_Engine SHALL include Recovery_Steps that list previous HEAD positions with `git reflog`, create a backup branch at the target commit with `git branch <backup-name> <commit>`, and verify the backup with `git log`.
3. WHEN the Incident_Text contains reflog entries, THE Fallback_Engine SHALL include the detected reflog entries in `detectedEvidence`.

### Requirement 8: Unknown and General Diagnosis

**User Story:** As a user with a Git problem that GitPulse does not recognize, I want a safe general response, so that I still receive useful inspection steps instead of an error or a wrong diagnosis.

#### Acceptance Criteria

1. IF the Incident_Text matches no Supported_Incident_Type pattern, THEN THE Fallback_Engine SHALL return an Analysis_Result with `incidentType` set to `unknown` and `confidence` set to `low`.
2. WHEN the Fallback_Engine returns an `unknown` Analysis_Result, THE Fallback_Engine SHALL include Recovery_Steps with Risk_Level `safe` only, using inspection commands such as `git status`, `git log --oneline -n 10`, and `git reflog -n 10`.
3. WHEN the Fallback_Engine returns an `unknown` Analysis_Result, THE Fallback_Engine SHALL include, in `assumptions`, a statement that GitPulse could not match the Incident_Text to a known incident type.
4. WHEN the Incident_Text matches patterns of more than one Supported_Incident_Type, THE Fallback_Engine SHALL select one Incident_Type using a documented fixed priority order and SHALL record the other matched Incident_Types in `assumptions`.

### Requirement 9: Analysis Result Data Contract

**User Story:** As a developer of GitPulse, I want one strict shared data contract between the Analyzer and the Dashboard, so that both Analysis_Modes produce results the Dashboard renders identically.

#### Acceptance Criteria

1. THE Analyzer SHALL return Analysis_Results that conform to the shared TypeScript interface with `incidentType` in {`rejected_push`, `merge_conflict`, `detached_head`, `stuck_rebase`, `lost_commits`, `unknown`}, `title` as string, `confidence` in {`high`, `medium`, `low`}, `severity` in {`low`, `medium`, `high`}, `analysisMode` in {`bedrock_ai`, `fallback_demo`}, `summary` as string, `detectedEvidence` as string array, `assumptions` as string array, and `recoverySteps` as an array of Recovery_Steps.
2. THE Analyzer SHALL return each Recovery_Step with `stepNumber` as number, `title` as string, `explanation` as string, `command` as string, `riskLevel` in {`safe`, `caution`, `destructive`}, optional `warningMessage` as string, and optional `backupPrerequisite` as string.
3. FOR ALL Analysis_Results returned by the Analyzer, THE Analyzer SHALL number Recovery_Steps with consecutive integers starting at 1 in display order.
4. FOR ALL Analysis_Results returned by the Analyzer, THE Analyzer SHALL include at least 1 Recovery_Step.
5. IF a response from the Bedrock_Handler fails validation against the shared interface, THEN THE Analyzer SHALL discard the response and SHALL produce the Analysis_Result with the Fallback_Engine.
6. FOR ALL valid Analysis_Results, serializing the Analysis_Result to JSON and parsing the JSON SHALL produce an Analysis_Result equal to the original (round-trip property).

### Requirement 10: Evidence Versus Assumptions

**User Story:** As a beginner, I want to see which facts GitPulse found in my output and which parts it is guessing, so that I can judge how far to trust the diagnosis.

#### Acceptance Criteria

1. FOR ALL Analysis_Results produced by the Fallback_Engine, THE Fallback_Engine SHALL include in `detectedEvidence` only entries derived from text present in the Incident_Text.
2. THE Fallback_Engine SHALL record in `assumptions` every inference that the Incident_Text does not directly show, such as the name of the remote, the branch, or whether uncommitted changes exist.
3. THE Dashboard SHALL display `detectedEvidence` and `assumptions` in 2 separately labeled lists titled "Detected Evidence" and "Assumptions".
4. IF `detectedEvidence` or `assumptions` is empty, THEN THE Dashboard SHALL display a placeholder message in the corresponding list stating that no entries are available.
5. WHEN the Incident_Text is a plain-language description without Git terminal output, THE Fallback_Engine SHALL set `confidence` to `medium` or `low`.
6. IF `detectedEvidence` contains fewer than 2 entries, THEN THE Analyzer SHALL set `confidence` to a value other than `high`.
7. THE Dashboard SHALL display the `confidence` value with the label "Confidence" and SHALL display wording that describes the diagnosis as likely, not certain.

### Requirement 11: Risky Command Validation Rules

**User Story:** As a beginner who might copy any command I see, I want GitPulse to flag risky commands, keep their warnings visible, and require the right safeguard steps for each specific command, so that I understand the remaining risk before I run anything.

#### Acceptance Criteria

1. THE Safety_Validator SHALL identify Risky_Commands by matching Git subcommand and option tokens in each Recovery_Step `command`, so that `--force-with-lease` is matched separately from `--force`, `-D` is matched separately from `-d`, and `-n` is matched separately from `-f`.
2. FOR ALL Analysis_Results, WHEN a Recovery_Step `command` contains a Risky_Command, THE Safety_Validator SHALL set the `riskLevel` of that Recovery_Step to the more severe of the `riskLevel` provided by the Fallback_Engine or the Bedrock_Handler and the Risk_Level defined for that Risky_Command in Requirements 12 through 15 (no-downgrade property).
3. FOR ALL Risky_Steps, THE Safety_Validator SHALL output a `riskLevel` of `caution` or `destructive`, including after the Safety_Validator inserts Safeguard_Steps before the Risky_Step.
4. FOR ALL Recovery_Steps whose input `warningMessage` is non-empty, THE Safety_Validator SHALL output a `warningMessage` that contains the input `warningMessage` text unchanged.
5. WHEN a Risky_Step `warningMessage` lacks the command-specific warning text defined in Requirements 12 through 15, THE Safety_Validator SHALL append the command-specific warning text to the `warningMessage`.
6. FOR ALL Risky_Steps, THE Safety_Validator SHALL output a `warningMessage` that contains the Residual_Risk_Label text exactly once.
7. IF a Recovery_Step has `riskLevel` `destructive`, contains no Risky_Command, and has an empty or missing `warningMessage`, THEN THE Safety_Validator SHALL set a non-empty `warningMessage` stating that the command can discard work or rewrite history and that the user should inspect the repository state before running the command.
8. WHEN the Safeguard_Window of a Risky_Step contains every Safeguard_Step of the required Safeguard_Set in the required relative order, THE Safety_Validator SHALL insert zero Safeguard_Steps for that Risky_Step.
9. WHEN the Safeguard_Window of a Risky_Step lacks part of the required Safeguard_Set, THE Safety_Validator SHALL determine the longest leading portion of the Safeguard_Set that appears in the required relative order within the Safeguard_Window and SHALL insert the remaining Safeguard_Steps of the Safeguard_Set, in the required order, immediately before the Risky_Step.
10. WHEN the Safety_Validator inserts a Safeguard_Step, THE Safety_Validator SHALL set the `riskLevel` of the inserted Safeguard_Step to `safe` and SHALL set a non-empty `title` and a non-empty `explanation` that states what the Safeguard_Step inspects or preserves and states that the Safeguard_Step reduces risk but does not make the following Risky_Step safe.
11. WHEN the Safety_Validator inserts one or more Safeguard_Steps, THE Safety_Validator SHALL renumber all Recovery_Steps with consecutive integers starting at 1.
12. FOR ALL Risky_Steps, THE Safety_Validator SHALL set `backupPrerequisite` to the commands of the required Safeguard_Set in the required order, joined by the separator ` then `.
13. WHEN a Recovery_Step `command` contains more than one Risky_Command, THE Safety_Validator SHALL apply the most severe Risk_Level among the contained Risky_Commands, SHALL include the command-specific warning text of every contained Risky_Command, and SHALL require the Safeguard_Sets of the contained Risky_Commands concatenated in order of appearance in the command.
14. FOR ALL Analysis_Results, applying the Safety_Validator twice SHALL produce the same Analysis_Result as applying the Safety_Validator once (idempotence property).
15. FOR ALL Analysis_Results, THE Safety_Validator SHALL preserve the relative order and content of the original non-inserted Recovery_Steps, apart from `stepNumber` renumbering, `riskLevel` severity increases, `warningMessage` text additions, and `backupPrerequisite` updates (invariant property).
16. THE Safety_Validator SHALL process every Analysis_Result from both the Fallback_Engine and the Bedrock_Handler before the Dashboard displays the Analysis_Result.
17. THE Dashboard SHALL display the `warningMessage` of each Recovery_Step with `riskLevel` `destructive` in a rose-colored warning callout adjacent to the command.
18. THE Dashboard SHALL display the `warningMessage` of each Recovery_Step with `riskLevel` `caution` in an amber-colored warning callout adjacent to the command.
19. WHEN a Recovery_Step `warningMessage` contains the Residual_Risk_Label text, THE Dashboard SHALL display the Residual_Risk_Label as a visible text badge next to the Risk_Badge of that Recovery_Step.
20. FOR ALL Risky_Steps, THE Safety_Validator SHALL output a `riskLevel` equal to the more severe of the input `riskLevel` and the classified Risk_Level of the contained Risky_Commands, both WHEN the Safeguard_Window already contains the complete Safeguard_Set and WHEN the Safety_Validator inserts Safeguard_Steps (safeguards never lower risk).
21. FOR ALL Risky_Steps, THE Safety_Validator SHALL output a `warningMessage` that contains the full input `warningMessage` text, the full command-specific warning text defined in Requirements 12 through 15, and the Residual_Risk_Label, both WHEN the Safeguard_Window already contains the complete Safeguard_Set and WHEN the Safety_Validator inserts Safeguard_Steps (safeguards never remove or shorten warnings).
22. FOR ALL Risky_Steps, THE Safety_Validator SHALL output a `warningMessage`, and FOR ALL inserted Safeguard_Steps an `explanation`, that contains zero Safety_Overclaim_Phrases.
23. THE Dashboard SHALL display, for every Risky_Step, the Risk_Badge text `caution` or `destructive` matching the output `riskLevel`, and SHALL display zero Safety_Overclaim_Phrases for any Risky_Step, including WHEN all Safeguard_Steps of the Safeguard_Set are present.

### Requirement 12: Hard Reset and Forced Checkout Safeguards

**User Story:** As a beginner about to discard local changes, I want GitPulse to make me inspect and preserve my uncommitted work first, so that a hard reset or forced checkout does not silently destroy changes that no backup branch protects.

#### Acceptance Criteria

1. WHEN a Recovery_Step `command` contains `git reset` with the `--hard` option, THE Safety_Validator SHALL classify the Risky_Command with Risk_Level `destructive`.
2. WHEN a Recovery_Step `command` contains `git reset` with the `--hard` option, THE Safety_Validator SHALL include in the `warningMessage` text stating that all uncommitted changes in the working tree and the staging area will be permanently discarded.
3. WHEN a Recovery_Step `command` contains `git reset` with the `--hard` option, THE Safety_Validator SHALL include in the `warningMessage` text stating that a backup branch protects commits but does not protect uncommitted changes.
4. WHEN a Recovery_Step `command` contains `git checkout` with the `-f` or `--force` option, THE Safety_Validator SHALL classify the Risky_Command with Risk_Level `destructive`.
5. WHEN a Recovery_Step `command` contains `git checkout` with the `-f` or `--force` option, THE Safety_Validator SHALL include in the `warningMessage` text stating that local modifications to tracked files will be permanently discarded when the checkout proceeds.
6. THE Safety_Validator SHALL require, for `git reset --hard` and for `git checkout -f`, the Safeguard_Set consisting of a `git status` inspection step followed by a change-preservation step with the default command `git stash push -u`.
7. THE Safety_Validator SHALL accept as matching the change-preservation Safeguard_Step only a `git stash push` command, or the implied-push shorthand `git stash` followed only by options, whose options include `-u`, `--include-untracked`, `-a`, `--all`, or a combined short-option group containing `u` or `a` (for example `git stash push -u`, `git stash push --include-untracked`, `git stash push -a`, `git stash push --all`, `git stash push -um "msg"`, `git stash -u`), and whose remaining options are limited to `-k`, `--keep-index`, `--no-keep-index`, `-q`, `--quiet`, `-m <msg>`, `--message=<msg>`, and `--message <msg>`.
8. WHEN the Safety_Validator inserts the change-preservation Safeguard_Step, THE Safety_Validator SHALL set an `explanation` stating that `git stash push -u` saves tracked, staged, and untracked non-ignored changes, that ignored files are not saved, and that `git stash pop` restores the saved changes.
9. WHEN a Recovery_Step `command` contains `git reset` with the `--hard` option or `git checkout` with the `-f` or `--force` option, THE Safety_Validator SHALL include in the `warningMessage` text stating that the `git status` and `git stash push -u` Safeguard_Steps reduce risk but do not guarantee that the command is safe.
10. WHEN a Recovery_Step `command` contains `git reset` with the `--hard` option or `git checkout` with the `-f` or `--force` option, THE Safety_Validator SHALL include in the `warningMessage` text stating that `git stash push -u` does not save ignored files and that only `git stash push -a` (`--all`) includes ignored files.
11. WHEN a Recovery_Step `command` contains `git reset` with the `--hard` option or `git checkout` with the `-f` or `--force` option, THE Safety_Validator SHALL include in the `warningMessage` text stating that data the Safeguard_Steps do not capture remains at risk, naming at least files outside the repository, unsaved editor buffers, and stash entries that can later be dropped or cleared.
12. WHEN the Safety_Validator inserts a `git status` or change-preservation Safeguard_Step for `git reset --hard` or `git checkout -f`, THE Safety_Validator SHALL set an `explanation` that states the Safeguard_Step does not protect ignored files or data outside the repository.
13. IF a Recovery_Step in the Safeguard_Window of `git reset --hard` or `git checkout -f` is any `git commit` command, plain `git stash`, a `git stash push` command without `-u`, `--include-untracked`, `-a`, or `--all`, or a `git stash save` command, THEN THE Safety_Validator SHALL NOT accept that step as matching the change-preservation Safeguard_Step.
14. IF a Recovery_Step in the Safeguard_Window of `git reset --hard` or `git checkout -f` is a partial stash using `-p`, `--patch`, `-S`, `--staged`, `--pathspec-from-file`, or any pathspec, THEN THE Safety_Validator SHALL NOT accept that step as matching the change-preservation Safeguard_Step.
15. IF a Recovery_Step in the Safeguard_Window of `git reset --hard` or `git checkout -f` contains a later `--no-include-untracked` or `--no-all` option that cancels an earlier untracked-files option, THEN THE Safety_Validator SHALL NOT accept that step as matching the change-preservation Safeguard_Step.

### Requirement 13: Git Clean Safeguards

**User Story:** As a beginner about to delete untracked files, I want GitPulse to make me preview exactly which files will be deleted, so that I do not permanently lose files that Git cannot recover.

#### Acceptance Criteria

1. WHEN a Recovery_Step `command` contains `git clean` with the `-f` or `--force` option, alone or combined in a short-option group such as `-fd`, `-fx`, or `-fdx`, THE Safety_Validator SHALL classify the Risky_Command with Risk_Level `destructive`.
2. WHEN a Recovery_Step `command` contains a `git clean` Destructive_Command, THE Safety_Validator SHALL include in the `warningMessage` text stating that untracked files will be permanently deleted and cannot be recovered with `git reflog` or `git stash`.
3. WHEN a `git clean` Destructive_Command includes the `-x` option, THE Safety_Validator SHALL include in the `warningMessage` text stating that ignored files, such as `.env` files and build outputs, will also be permanently deleted.
4. WHEN a `git clean` Destructive_Command includes the `-X` option, THE Safety_Validator SHALL include in the `warningMessage` text stating that ignored files will be permanently deleted.
5. THE Safety_Validator SHALL require, for each `git clean` Destructive_Command, a Safeguard_Set consisting of 1 dry-run Safeguard_Step whose command is `git clean -n` combined with the same `-d`, `-x`, and `-X` options and the same pathspec arguments as the Destructive_Command, such as `git clean -n` for `git clean -f`, `git clean -nd` for `git clean -fd`, `git clean -nx` for `git clean -fx`, and `git clean -ndx` for `git clean -fdx`.
6. THE Safety_Validator SHALL accept as the matching dry-run Safeguard_Step any `git clean` command that contains the `-n` or `--dry-run` option, contains no `-f` or `--force` option, and contains the same set of `-d`, `-x`, and `-X` options and pathspec arguments as the Destructive_Command, in any option order or grouping.
7. WHEN the Safety_Validator inserts the dry-run Safeguard_Step, THE Safety_Validator SHALL set an `explanation` stating that the dry run lists the files that the cleanup command would delete and deletes no files.
8. WHEN a Recovery_Step `command` contains `git clean` with the `-n` or `--dry-run` option and without the `-f` or `--force` option, THE Safety_Validator SHALL classify the Recovery_Step as containing no Risky_Command.

### Requirement 14: Force Push Safeguards

**User Story:** As a developer about to force push, I want GitPulse to explain that I can overwrite teammates' commits and make me compare my branch with the remote first, so that I do not destroy shared history.

#### Acceptance Criteria

1. WHEN a Recovery_Step `command` contains `git push` with the `--force` option or the `-f` option, THE Safety_Validator SHALL classify the Risky_Command with Risk_Level `destructive`.
2. WHEN a Recovery_Step `command` contains `git push` with the `--force-with-lease` option and without the `--force` or `-f` option, THE Safety_Validator SHALL classify the Risky_Command with Risk_Level `caution`.
3. WHEN a Recovery_Step `command` contains `git push` with the `--force` or `-f` option, THE Safety_Validator SHALL include in the `warningMessage` text stating that the push overwrites the remote branch history and removes commits that teammates pushed and that the local branch lacks.
4. WHEN a Recovery_Step `command` contains `git push` with the `--force` or `-f` option, THE Safety_Validator SHALL include in the `warningMessage` text recommending `git push --force-with-lease` only for a personal branch after a rebase, and stating that rewriting a shared branch such as `main` requires coordination with teammates first.
5. WHEN a Recovery_Step `command` contains a `git push --force-with-lease` Caution_Command, THE Safety_Validator SHALL include in the `warningMessage` text stating that the push still rewrites remote history, that the lease protects only against remote commits not yet fetched, and that a fetch without inspection makes the lease check pass for commits the user has not reviewed.
11. WHEN a Recovery_Step `command` contains a `git push --force-with-lease` Caution_Command, THE Safety_Validator SHALL include in the `warningMessage` text stating that the user should consider the push only after inspecting the remote changes with the `git fetch` and `git log --oneline HEAD..<remote>/<branch>` Safeguard_Steps, confirming that the target branch is the intended branch, and confirming that the team workflow permits rewriting the branch (the branch is personal or teammates agreed to the rewrite).
12. FOR ALL Recovery_Steps containing a `git push --force-with-lease` Caution_Command, THE Safety_Validator SHALL output a `riskLevel` of `caution` or `destructive`, the warning text from criteria 5 and 11, and the Residual_Risk_Label, including WHEN the Safeguard_Window already contains the complete Safeguard_Set.
6. THE Safety_Validator SHALL require, for every `git push` Risky_Command, the Safeguard_Set consisting of a `git fetch <remote>` step followed by an inspection step with the command `git log --oneline HEAD..<remote>/<branch>`.
7. WHEN the `git push` Risky_Command names a remote and a branch, THE Safety_Validator SHALL use the named remote and branch in the inserted Safeguard_Steps.
8. IF the `git push` Risky_Command omits the remote or the branch, THEN THE Safety_Validator SHALL use `origin` for the omitted remote and the placeholder `<branch>` for the omitted branch in the inserted Safeguard_Steps.
9. THE Safety_Validator SHALL accept any `git fetch` command as matching the fetch Safeguard_Step and any `git log` command containing a `HEAD..<remote>/<branch>` range as matching the inspection Safeguard_Step.
10. WHEN the Safety_Validator inserts the inspection Safeguard_Step, THE Safety_Validator SHALL set an `explanation` stating that each listed commit exists only on the remote and will be removed from the remote branch by the force push.

### Requirement 15: Force Branch Deletion Safeguards

**User Story:** As a developer about to force-delete a branch, I want GitPulse to make me check for unmerged commits first, so that I do not lose work that exists only on that branch.

#### Acceptance Criteria

1. WHEN a Recovery_Step `command` contains `git branch` with the `-D` option, or with both a delete option (`-d` or `--delete`) and a force option (`-f` or `--force`), THE Safety_Validator SHALL classify the Risky_Command with Risk_Level `destructive`.
2. WHEN a Recovery_Step `command` contains a `git branch` Destructive_Command, THE Safety_Validator SHALL include in the `warningMessage` text stating that unmerged commits on the deleted branch stop being reachable from any branch and remain recoverable through `git reflog` only for a limited time before Git garbage collection removes the commits.
3. WHEN a Recovery_Step `command` contains a `git branch` Destructive_Command, THE Safety_Validator SHALL include in the `warningMessage` text suggesting the optional backup command `git tag backup/<branch> <branch>` before deletion.
4. THE Safety_Validator SHALL require, for each `git branch` Destructive_Command, the Safeguard_Set consisting of an inspection step with the command `git log --oneline <branch>` followed by an inspection step with the command `git branch --no-merged`, where `<branch>` is the branch name from the Destructive_Command.
5. THE Safety_Validator SHALL accept any `git log` command naming the deleted branch as matching the first Safeguard_Step and any `git branch --no-merged` command as matching the second Safeguard_Step.
6. WHEN a Recovery_Step `command` contains `git branch` with the `-d` or `--delete` option and without the `-D`, `-f`, or `--force` option, THE Safety_Validator SHALL classify the Recovery_Step as containing no Risky_Command.

THE Test_Suite SHALL include Vitest unit tests verifying that, for Recovery_Steps with commands `git clean -f`, `git clean -fd`, `git clean -fx`, and `git clean -fdx`, the Safety_Validator outputs `riskLevel` `destructive`, the permanent-deletion warning text from Requirement 13, the ignored-files warning text for the `-x` variants, the matching dry-run Safeguard_Step (`git clean -n`, `git clean -nd`, `git clean -nx`, `git clean -ndx` respectively) immediately before the Risky_Step, and the Residual_Risk_Label.
3. THE Test_Suite SHALL include Vitest unit tests verifying that, for Recovery_Steps with commands `git push --force origin feature` and `git push -f origin feature`, the Safety_Validator outputs `riskLevel` `destructive`, the overwrite and `--force-with-lease` recommendation warning text from Requirement 14, the Safeguard_Steps `git fetch origin` and `git log --oneline HEAD..origin/feature` in that order immediately before the Risky_Step, and the Residual_Risk_Label.

THE Test_Suite SHALL include a Vitest unit test verifying that, for a Recovery_Step with command `git push --force-with-lease origin feature`, the Safety_Validator outputs `riskLevel` `caution`, the `--force-with-lease` warning text from Requirement 14, the Safeguard_Steps `git fetch origin` and `git log --oneline HEAD..origin/feature` in that order immediately before the Risky_Step, and the Residual_Risk_Label.
5. THE Test_Suite SHALL include a Vitest unit test verifying that, for a Recovery_Step with command `git checkout -f main`, the Safety_Validator outputs `riskLevel` `destructive`, the tracked-file modification warning text from Requirement 12, the Safeguard_Steps `git status` and `git stash push -u` in that order immediately before the Risky_Step, and the Residual_Risk_Label.

THE Test_Suite SHALL include a Vitest unit test verifying that, for a Recovery_Step with command `git branch -D feature`, the Safety_Validator outputs `riskLevel` `destructive`, the reflog time-limit and backup-tag warning text from Requirement 15, the Safeguard_Steps `git log --oneline feature` and `git branch --no-merged` in that order immediately before the Risky_Step, and the Residual_Risk_Label.

### Requirement 17: Recovery Plan Display

**User Story:** As a beginner, I want each recovery step to explain what to do, why it works, and the exact command, so that I understand every action before I run it.

#### Acceptance Criteria

1. WHEN the Analyzer returns an Analysis_Result, THE Dashboard SHALL display the `title`, `summary`, `incidentType`, `severity`, `confidence`, and Mode_Badge of the Analysis_Result.
2. WHEN the Analyzer returns an Analysis_Result, THE Dashboard SHALL display the Recovery_Steps in ascending `stepNumber` order.
3. THE Dashboard SHALL display, for each Recovery_Step, the `stepNumber`, `title`, `explanation`, Risk_Badge, and `command` in a monospace terminal-styled card.
4. THE Dashboard SHALL color Risk_Badges emerald for `safe`, amber for `caution`, and rose for `destructive`, each with a text label showing the Risk_Level.
5. WHEN a Recovery_Step has a `backupPrerequisite`, THE Dashboard SHALL display the `backupPrerequisite` with a label stating that the user should run the prerequisite first.

### Requirement 18: Copy Command and Manual Execution

**User Story:** As a user following a recovery plan, I want to copy a command with one click and decide myself whether to run it, so that I avoid typos and stay in control of every change to my repository.

#### Acceptance Criteria

1. THE Dashboard SHALL display a copy button on each Recovery_Step command card.
2. WHEN the user activates a copy button, THE Dashboard SHALL write the exact `command` string of that Recovery_Step to the system clipboard.
3. WHEN the clipboard write succeeds, THE Dashboard SHALL change the copy button to a "Copied" confirmation state for 2 seconds and then restore the default state.
4. IF the clipboard write fails, THEN THE Dashboard SHALL display a message stating that copying failed and that the user can select the command text manually.
5. THE GitPulse SHALL execute zero Git commands and SHALL make zero modifications to the user's file system or repositories; the user runs every command manually in a terminal.
6. THE Dashboard SHALL present each Recovery_Step `command` as selectable, read-only text whose only action control is the copy button, with zero controls that run, execute, or send the command to a terminal.
7. WHEN the Dashboard displays a Recovery_Step with `riskLevel` `caution` or `destructive`, THE Dashboard SHALL display, adjacent to the copy button, a reminder stating that the user should review the command and its safeguard steps before running the command manually in a terminal.
8. THE Analyzer and THE Bedrock_Handler SHALL execute zero Git commands and SHALL operate only on the submitted Incident_Text, with zero access to the user's repository or file system.
9. THE GitPulse SHALL send network requests only to the origin serving the static frontend and, WHERE the Bedrock_Endpoint_URL is configured, to the Bedrock_Endpoint_URL, with zero requests to Git remote hosts.

### Requirement 19: Analysis Mode Selection and Honest Disclosure

**User Story:** As a user, I want to know whether a diagnosis came from Amazon Bedrock or from the deterministic fallback engine, so that I am not misled about how the answer was generated.

#### Acceptance Criteria

1. WHERE the Bedrock_Endpoint_URL is configured, WHEN the user starts an analysis, THE Analyzer SHALL send the Incident_Text to the Bedrock_Handler.
2. WHERE the Bedrock_Endpoint_URL is not configured, WHEN the user starts an analysis, THE Analyzer SHALL produce the Analysis_Result with the Fallback_Engine.
3. IF the Bedrock_Handler returns an error, returns an invalid response, or does not respond within 15 seconds, THEN THE Analyzer SHALL produce the Analysis_Result with the Fallback_Engine.
4. WHEN the Analyzer falls back after a Bedrock_Handler failure, THE Dashboard SHALL display a notice stating that Amazon Bedrock was unavailable and that the result came from Deterministic Fallback / Demo Mode.
5. THE Fallback_Engine SHALL set `analysisMode` to `fallback_demo` on every Analysis_Result the Fallback_Engine produces.
6. THE Analyzer SHALL set `analysisMode` to `bedrock_ai` only on Analysis_Results whose content was generated by a successful Bedrock_Handler response.
7. WHEN an Analysis_Result has `analysisMode` `bedrock_ai`, THE Dashboard SHALL display the Mode_Badge with the text "Amazon Bedrock AI".
8. WHEN an Analysis_Result has `analysisMode` `fallback_demo`, THE Dashboard SHALL display the Mode_Badge with the text "Deterministic Fallback / Demo Mode".
9. THE Dashboard SHALL display the Mode_Badge on every displayed Analysis_Result, including Analysis_Results reloaded from the History_Panel.

### Requirement 20: Analysis History

**User Story:** As a user, I want to see and reload my recent analyses, so that I can return to a previous recovery plan without pasting the error again.

#### Acceptance Criteria

1. WHEN the Analyzer returns an Analysis_Result, THE History_Store SHALL save a History_Entry containing the Incident_Text, the Analysis_Result, and the creation timestamp in `localStorage`.
2. THE History_Store SHALL retain at most 10 History_Entries and SHALL remove the oldest History_Entry when an 11th History_Entry is saved.
3. THE History_Panel SHALL list History_Entries in descending creation-timestamp order, showing the Analysis_Result `title`, the Mode_Badge, and the creation time for each History_Entry.
4. WHEN the user selects a History_Entry, THE Dashboard SHALL restore the Incident_Text into the Incident_Input and SHALL display the stored Analysis_Result without starting a new analysis.
5. WHEN the user activates the clear-history control, THE History_Store SHALL remove all History_Entries from `localStorage` and THE History_Panel SHALL display the empty history state.
6. WHEN the Dashboard loads, THE History_Store SHALL read History_Entries saved in `localStorage` by earlier sessions.
7. IF the stored history data in `localStorage` is unreadable or fails validation, THEN THE History_Store SHALL discard the invalid data and SHALL start with an empty history.
8. IF writing to `localStorage` fails, THEN THE Dashboard SHALL keep displaying the current Analysis_Result and SHALL display a message stating that history could not be saved.
9. FOR ALL valid lists of History_Entries, saving the list to `localStorage` and loading the list SHALL produce an equal list (round-trip property).

### Requirement 21: Interface States

**User Story:** As a user, I want clear empty, loading, validation, and error states, so that I always know what GitPulse is doing.

#### Acceptance Criteria

1. WHILE no Analysis_Result is displayed, THE Dashboard SHALL display an empty state that instructs the user to paste Git output or select a Sample_Incident.
2. WHILE an analysis is in progress, THE Dashboard SHALL display a loading indicator and SHALL disable the "Analyze Incident" button.
3. WHILE the History_Store contains zero History_Entries, THE History_Panel SHALL display an empty history message.
4. IF the Analyzer fails to produce any Analysis_Result, THEN THE Dashboard SHALL display an error state with a description of the failure and a retry control.
5. WHEN the Fallback_Engine analyzes an Incident_Text of up to 20,000 characters, THE Fallback_Engine SHALL return the Analysis_Result within 500 milliseconds on a mid-range laptop browser.

### Requirement 22: Visual Design and Accessibility

**User Story:** As a developer, I want a polished dark dashboard that is readable on desktop and mobile, so that GitPulse is pleasant and accessible to use.

#### Acceptance Criteria

1. THE Dashboard SHALL use a dark theme with slate-950 and slate-900 surface colors, cyan and violet accent colors, and monospace fonts for command and terminal content.
2. WHILE the viewport width is at least 1024 pixels, THE Dashboard SHALL display the Incident_Input area and the Analysis_Result area in a 2-column layout.
3. WHILE the viewport width is less than 1024 pixels, THE Dashboard SHALL display all sections in a single-column layout.
4. THE Dashboard SHALL render text with a contrast ratio of at least 4.5:1 against its background, meeting WCAG 2.1 AA for normal text.
5. THE Dashboard SHALL make every interactive control reachable and operable by keyboard with a visible focus indicator.
6. THE Dashboard SHALL provide accessible names for all icon-only buttons, including copy buttons.
7. THE Dashboard SHALL convey Risk_Level with a text label in addition to color.

### Requirement 23: Static Deployment

**User Story:** As a hackathon participant, I want the frontend to deploy as a static site without any backend, so that GitPulse can be deployed and demonstrated today.

#### Acceptance Criteria

1. THE GitPulse SHALL produce a static frontend build with the Vite build command that is deployable on AWS Amplify Hosting, Vercel, or Netlify.
2. WHERE the Bedrock_Endpoint_URL is not configured, THE GitPulse SHALL complete the full core workflow (input, sample incidents, analysis, safety validation, recovery plan display, copy, reset, and history) in `fallback_demo` mode.
3. THE GitPulse SHALL contain no database, user authentication, GitHub OAuth, or live repository integration.
4. THE Test_Suite SHALL cover the Fallback_Engine, the Safety_Validator (including every risky command case listed in Requirement 16), the Analysis_Result validation, and the History_Store.
5. THE GitPulse SHALL treat the `fallback_demo` core app (Dashboard, Fallback_Engine, Sample_Incidents, Safety_Validator, History_Store) and the Test_Suite as the first implementation priority, and SHALL treat the Bedrock_Handler as an optional addition built after the core app.
6. THE Vite build command and THE Test_Suite SHALL complete successfully with zero AWS credentials configured, with the AWS SDK not installed, and with the dependencies of the `backend/` directory not installed.
7. THE frontend source code SHALL contain zero imports from the `backend/` directory and zero imports of AWS SDK packages.

### Requirement 24: Optional Bedrock Lambda Handler

**User Story:** As a developer with an AWS account, I want an optional Lambda handler that calls Amazon Bedrock, so that I can enable AI-generated diagnoses without exposing credentials in the browser.

#### Acceptance Criteria

1. THE Bedrock_Handler SHALL be implemented in `backend/lambda/analyzeIncident.ts` and SHALL accept an HTTP POST request with a JSON body containing an `incidentText` string.
2. WHEN the Bedrock_Handler receives a valid request, THE Bedrock_Handler SHALL call Amazon Bedrock and SHALL return an HTTP 200 response whose body is an Analysis_Result with `analysisMode` set to `bedrock_ai`.
3. IF the request body is missing `incidentText`, contains an empty `incidentText`, or contains an `incidentText` longer than 20,000 characters, THEN THE Bedrock_Handler SHALL return an HTTP 400 response with a JSON error message.
4. IF the Amazon Bedrock call fails or the Bedrock output fails validation against the shared interface, THEN THE Bedrock_Handler SHALL return an HTTP 502 response with a JSON error message.
5. THE Bedrock_Handler SHALL read AWS region, Bedrock model identifier, and credentials only from environment variables or the Lambda execution role.
6. THE GitPulse SHALL contain zero AWS credentials in frontend source code and in the static frontend build output.
7. THE Bedrock_Handler SHALL instruct the Amazon Bedrock model to return output matching the shared Analysis_Result interface, to separate detected evidence from assumptions, and to avoid claiming certainty when evidence is partial.
8. THE Bedrock_Handler SHALL return CORS headers that permit requests from the configured frontend origin.
9. THE GitPulse SHALL include a deployment guide that documents the Bedrock_Handler API contract, the required environment variables, the Amplify Hosting deployment steps, and the Bedrock_Endpoint_URL configuration.
10. THE Bedrock_Handler SHALL declare the AWS SDK and other backend dependencies in a dependency manifest separate from the frontend dependency manifest, so that installing frontend dependencies installs zero AWS SDK packages.
11. WHERE the Bedrock_Handler is not built or deployed, THE GitPulse SHALL provide the full core workflow defined in Requirement 23 criterion 2.
